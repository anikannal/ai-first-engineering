# Assessment Rubrics
### AI-First Software Engineering Bootcamp

---

## Overview

The program uses three core assessment types across all three phases. They are designed to be complementary — each tests a different dimension of what it means to be an effective AI-first engineer.

| Assessment | What it tests | When it runs |
|---|---|---|
| **Code Walkthrough** | Individual comprehension and critical judgment | End of Phase 1, Phase 2, Phase 3 |
| **PR History Review** | Engineering discipline and AI collaboration quality | End of Phase 2, Phase 3 |
| **Portfolio Artifact** | Reflective practice and communication | End of Phase 3 |

There are no written exams. There are no LeetCode-style algorithmic tests. Assessment is entirely grounded in the work students actually do.

---

## Assessment 1: Code Walkthrough

### Purpose

The code walkthrough is the primary check against surface-level AI usage. It verifies that a student understands the codebase they've contributed to — including sections generated by AI — and can reason about it critically.

A student who can prompt AI to generate working code but cannot explain what it does is not yet an engineer. This assessment closes that gap.

### Format

- **Duration:** 10–15 minutes per student
- **Conducted by:** Human Engineering Coach (1:1)
- **Timing:** End of each phase (Weeks 5, 11, 16)
- **What's assessed:** The assessor selects 2–3 sections of the student's squad codebase in advance — including at least one section the student did not personally author (could be AI-generated or written by a squadmate). The student is not told in advance which sections will be chosen.

### Procedure

1. The assessor shares the screen showing the selected code section
2. The student explains it in their own words (no preparation, no notes)
3. The assessor asks follow-up questions (see question bank below)
4. The assessor introduces a hypothetical change or bug and asks the student to reason through it

### Question Bank (Assessor Reference)

**Comprehension:**
- "Walk me through what this function does, step by step."
- "What would happen if this input was empty? Or null?"
- "Why do you think this was structured this way?"

**Critical evaluation:**
- "Is there anything here you'd change? Why?"
- "Do you see any edge cases this doesn't handle?"
- "If this was AI-generated, what would you want to verify before shipping it?"

**Ownership:**
- "Did you write this, or did the AI? If the AI — did you change anything?"
- "What would break in the rest of the system if this function was removed?"
- "If a new developer joined the team, what would you tell them about this part of the codebase?"

---

### Rubric

Each student is scored across four dimensions on a 1–4 scale.

**1 — Developing** | **2 — Approaching** | **3 — Meets Standard** | **4 — Exceeds Standard**

---

#### Dimension 1: Comprehension

*Can the student accurately explain what the code does?*

| Score | Description |
|-------|-------------|
| 1 | Cannot explain the code's purpose. Describes what they see syntactically ("it's a function, it has parameters") without meaning. |
| 2 | Can explain the general purpose but misses key details or gets some behaviour wrong. |
| 3 | Accurately explains what the code does, including inputs, outputs, and side effects. May need a prompt or two to get there. |
| 4 | Explains the code fluently and precisely, including edge cases and how it fits into the broader system, without prompting. |

---

#### Dimension 2: Critical Evaluation

*Does the student evaluate the code, not just describe it?*

| Score | Description |
|-------|-------------|
| 1 | Accepts the code as-is. Cannot identify any potential issues or improvements even when prompted. |
| 2 | Identifies one obvious issue or improvement when explicitly asked, but cannot reason about why it matters. |
| 3 | Proactively identifies at least one potential issue or improvement and can explain the reasoning. |
| 4 | Identifies multiple issues or improvements, reasons about tradeoffs, and suggests a concrete path forward. Treats the code with appropriate scepticism. |

---

#### Dimension 3: AI Awareness

*Does the student understand how AI contributed to this code, and what that means?*

| Score | Description |
|-------|-------------|
| 1 | Cannot distinguish between AI-generated and human-written sections. Has not thought about this. |
| 2 | Aware that AI generated some code but cannot explain what they verified, changed, or decided to keep. |
| 3 | Can articulate what AI generated, what they changed, what they verified, and why they trusted (or didn't trust) the output. |
| 4 | Demonstrates sophisticated AI collaboration judgment: knows when to accept, modify, or reject AI output, and can explain the heuristics they've developed. |

---

#### Dimension 4: System Thinking

*Does the student understand this code in context, not in isolation?*

| Score | Description |
|-------|-------------|
| 1 | Can only discuss the code in isolation. Cannot reason about how it connects to or affects the rest of the system. |
| 2 | Has a vague sense of the code's place in the system but cannot trace dependencies or consequences clearly. |
| 3 | Can explain how this code connects to adjacent parts of the system and what would break if it changed. |
| 4 | Reasons fluently about the code's role in the system, identifies implicit dependencies, and considers downstream effects of changes. |

---

#### Scoring Summary

| Total Score | Outcome |
|-------------|---------|
| 13–16 | Distinction |
| 10–12 | Pass |
| 7–9 | Borderline — coaching conversation required |
| 4–6 | Does not meet standard — remediation plan required |

**Minimum passing score:** 10. A score of 1 on any single dimension, regardless of total, triggers a mandatory coaching conversation.

## Assessment 2: PR History Review

### Purpose

Software engineering is not just about the code you produce — it's about how you work. The PR History Review assesses the quality of a student's engineering practice across a phase: how they collaborated, how they used AI, how they reviewed others' code, and whether their commit history reflects genuine understanding.

### Format

- **Duration:** Asynchronous review by Engineering Coach + 15-minute feedback conversation
- **Timing:** End of Phase 2 (Week 11) and Phase 3 (Week 16)
- **What's assessed:** The student's full PR history for the phase — both PRs they authored and PRs they reviewed

### What the Assessor Reviews

**PRs authored:**
- PR description quality: does it explain what changed and why?
- Commit message quality: are commits atomic and descriptive?
- Response to review comments: did the student engage thoughtfully or just make the minimum change?
- Evidence of AI use: were AI-generated changes explained and validated in the PR description?

**PRs reviewed:**
- Review thoroughness: did the student do more than approve?
- Quality of comments: are they specific, constructive, and reasoned?
- Engagement with AI-generated code: did they treat AI-generated sections with appropriate scrutiny?

---

### Rubric

#### Dimension 1: PR Communication

*Do the student's PRs tell a clear story of what changed and why?*

| Score | Description |
|-------|-------------|
| 1 | PR descriptions are absent, minimal ("fixed stuff"), or just a list of files changed. |
| 2 | PRs have descriptions but they focus on what changed technically, not why the change was made or what it accomplishes. |
| 3 | PRs are clearly written: they explain the purpose of the change, reference the relevant task, and note anything the reviewer should pay attention to. |
| 4 | PRs are exemplary: they include context, highlight tradeoffs considered, flag AI-generated sections explicitly, and make the reviewer's job easy. |

---

#### Dimension 2: Commit Discipline

*Do commits reflect intentional, understandable progress?*

| Score | Description |
|-------|-------------|
| 1 | Commits are infrequent, enormous ("added everything"), or have no meaningful messages. |
| 2 | Commits are somewhat frequent but inconsistently sized and messaged. Hard to follow the development narrative. |
| 3 | Commits are reasonably atomic and have clear messages that describe what changed in that commit. |
| 4 | Commit history reads like a clear narrative of the feature being built. Anyone could follow the development progression from commits alone. |

---

#### Dimension 3: AI Collaboration Transparency

*Is the student's use of AI visible, honest, and thoughtful in their PR history?*

| Score | Description |
|-------|-------------|
| 1 | No evidence that the student thought about AI's role in their code. AI-generated sections are undifferentiated from hand-written code. |
| 2 | Occasionally notes AI involvement but inconsistently and without reflection on what was verified or changed. |
| 3 | Consistently notes significant AI contributions in PR descriptions, explains what was verified or modified, and flags any areas of uncertainty. |
| 4 | Treats AI as a collaborator to be cited and evaluated. PR descriptions include clear AI attribution and demonstrate critical judgment about AI output quality. |

---

#### Dimension 4: Review Quality

*Do the student's code reviews add genuine value?*

| Score | Description |
|-------|-------------|
| 1 | Reviews are absent or consist only of approvals with no comments. |
| 2 | Reviews include some comments but they are superficial (typos, formatting) rather than substantive. |
| 3 | Reviews include at least one substantive comment per PR that identifies a real issue, asks a clarifying question, or suggests a meaningful improvement. |
| 4 | Reviews are thorough and add clear value: they identify non-obvious issues, engage with AI-generated code critically, and explain the reasoning behind every comment. |

---

#### Scoring Summary

| Total Score | Outcome |
|-------------|---------|
| 13–16 | Distinction |
| 10–12 | Pass |
| 7–9 | Borderline — coaching conversation required |
| 4–6 | Does not meet standard — remediation plan required |

## Assessment 3: Portfolio Artifact

### Purpose

The portfolio artifact is the culminating individual assessment. It asks students to reflect honestly on their journey through the program — not just what they built, but how they built it, what they learned about working with AI, and who they are as an engineer.

This is also a career document. A well-executed portfolio artifact is something a student can share with employers to demonstrate not just what they made, but how they think.

### Format

- **Medium:** Student's choice — written case study (1,500–2,500 words), video essay (8–12 minutes), or structured presentation (15 slides + speaker notes)
- **Timing:** Submitted end of Phase 3 (Week 16), prior to Demo Day
- **Audience:** Written for a technical hiring manager or senior engineer at a software company

### Required Content

The artifact must address all five of the following:

**1. The product**
What did you build? Who is it for? What problem does it solve? Include a link to the live product and the GitHub repository.

**2. The build journey**
How did the product evolve from Week 1 to Week 16? What were the major technical decisions, and who made them (you, your squad, the AI)?

**3. AI collaboration — what worked**
Give 2–3 specific examples of AI assistance that genuinely accelerated your work. What did you prompt? What did it produce? What did you do with it?

**4. AI collaboration — what didn't work**
Give 2–3 specific examples of AI assistance that failed, misled you, or produced code you had to significantly revise. What happened? What did you learn? What would you do differently?

**5. Who you are as an engineer now**
What's your mental model for when to use AI and when not to? What habits have you developed? What do you still want to get better at?

---

### Rubric

#### Dimension 1: Honesty and Depth of Reflection

*Does the artifact go beyond surface-level summary to genuine reflection?*

| Score | Description |
|-------|-------------|
| 1 | Reads as a product description or feature list. No real reflection on process, decisions, or AI use. |
| 2 | Some reflection present but stays at a generic level ("AI helped me code faster"). Doesn't engage with specific examples or genuine challenges. |
| 3 | Specific, honest reflection on both successes and failures with AI. The reader learns something real about how this student worked. |
| 4 | Exceptionally honest and insightful. Surfaces non-obvious lessons, acknowledges genuine mistakes, and demonstrates a mature relationship with AI as a tool — neither uncritical enthusiasm nor reflexive scepticism. |

---

#### Dimension 2: Technical Credibility

*Does the artifact demonstrate genuine technical understanding?*

| Score | Description |
|-------|-------------|
| 1 | Technical content is vague or incorrect. Could have been written without actually building anything. |
| 2 | Technical content is present but superficial. Describes what was built without demonstrating understanding of how or why. |
| 3 | Technical explanations are accurate and appropriately detailed. The reader can tell this student knows what they built. |
| 4 | Technical content is precise and confident. The student can explain architectural decisions, tradeoffs, and the implications of their choices. Goes beyond describing the code to reasoning about it. |

---

#### Dimension 3: Specificity of AI Examples

*Are the AI collaboration examples concrete and instructive?*

| Score | Description |
|-------|-------------|
| 1 | AI examples are absent or entirely generic ("I used Claude to help write code"). |
| 2 | Some specific examples given but without enough context to be instructive. |
| 3 | Clear, specific examples with enough context (what was the task, what was the prompt, what was produced, what was changed) that a reader could learn from them. |
| 4 | Examples are exemplary case studies in AI collaboration. They include the actual prompts used, the quality of the AI output, the student's evaluation process, and the final result. Genuinely instructive for anyone trying to develop AI-first engineering skills. |

---

#### Dimension 4: Communication Quality

*Is the artifact well-crafted for its intended audience?*

| Score | Description |
|-------|-------------|
| 1 | Poorly structured, hard to follow, or clearly written in a rush. Would not be appropriate to share with an employer. |
| 2 | Readable but unpolished. Structure is present but not compelling. Technical terminology used inconsistently or incorrectly. |
| 3 | Well-structured, clearly written, and appropriate for a technical audience. Would represent the student well in a job application context. |
| 4 | Distinctive and compelling. The student's voice and perspective come through. Would stand out positively in any hiring context. |

---

#### Scoring Summary

| Total Score | Outcome |
|-------------|---------|
| 13–16 | Distinction |
| 10–12 | Pass |
| 7–9 | Borderline — revision opportunity offered |
| 4–6 | Does not meet standard — full revision required |

## AI Coach Role in Assessments

The AI Coach supports assessment without replacing human judgment on outcomes.

| Assessment stage | AI Coach involvement |
|---|---|
| **Before Code Walkthrough** | Course Coordinator surfaces a pre-brief for the assessor: student's phase progress, reflection themes, any flagged blockers |
| **During Code Walkthrough** | None — this is a human-only interaction by design |
| **PR History preparation** | Code Review Agent flags patterns in the student's PR history for the assessor to explore |
| **Portfolio Artifact drafting** | Reflection Interviewer helps students identify and articulate key examples from their weekly reflections |
| **Portfolio Artifact review** | None — human assessor reads and scores independently |

The rule: AI can help students prepare and help assessors surface relevant context. AI does not score.
